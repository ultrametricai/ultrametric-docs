> Internal documentation draft. These storage semantics are source-inspected; hosted writes were not exercised.

| Term | Meaning |
| --- | --- |
| Process | Instructions and a result schema for an outcome |
| Run | A saved instance of work for an organization, company, process, and optional recurring period |
| Context | Company profiles, documents, references, and reported progress available to authorized callers |
| Revision | An append-only change to saved information |
| Receipt | Confirmation that the service accepted a particular save |

## Read before recording

`get_process` retrieves a guide. `get_context` reads authorized records. `open_process` starts or resumes a run and can create the initial company when none exists. It returns the guide, existing context, organization ID, run ID, and next update key. These are separate operations with different effects.

The CLI equivalents are `process get`, `context get`, and `process open`. CLI `companies` and `assessments` use local files. They do not automatically synchronize to hosted context.

## Save progress with a receipt

`save_update` and CLI `context save` record progress and optional profile, document, reference, or deletion changes. Use the organization ID, run ID, and next update key from the preceding result. Existing records require their current revision.

A successful save supplies a receipt with `saved`, `revision`, `savedAt`, `nextUpdateKey`, and record revisions. After an uncertain save, retry the exact input with the same update key. A new change uses the returned next key. Resolve conflicts by reading current state rather than generating another key and repeating an effect.

Current reads exclude deleted and superseded records. History requires an explicit record or run selector. Deletion appends a tombstone; it does not rewrite prior revisions.

## Keep review separate from effects

The agent prepares results from available context and asks for necessary facts, consequential choices, or authority missing from the user's request. Reuse approval already provided for the same action and scope.

Profile review metadata records what the caller reports. The API does not verify that a human approved it. CLI local profile saving checks for review evidence and valid structure; it does not prove that evidence is true. A run marked `completed` records reported progress and does not prove an external action succeeded.

Before a filing, payment, account change, or other external effect, use the relevant tool's authorization rules and the user's scope. Preserve the external system's confirmation separately from a saved process update.

## Keep private context in its selected scope

Private operations require the selected organization, active membership, and context permissions. Read/write and protected-data permissions are distinct. Passing an organization ID checks the login's scope; it does not switch membership.

Do not store secret values. Vault references use protected visibility. Mark other sensitive records appropriately; the API's pattern checks cannot identify every sensitive field. See [authentication and scope](/mcp/authentication).
